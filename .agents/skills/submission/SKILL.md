# Hackathon Submission

## Read first

- `docs/HACKATHON_SOURCE_OF_TRUTH.md`

- current official rules before final submission.

## Judge-first principle

Judges may never run the code. The video/description/screenshots must communicate a working, technically credible product without relying on README archaeology.

## Three-minute story

Target structure, refine with real product timings:

### 0:00–0:20 — Pain

Show active work + interruption. Establish that files persist but mental state does not.

### 0:20–0:45 — Park

"Alexa, park this." Show cognitive checkpoint forming from real evidence.

### 0:45–1:25 — Return + magic

Change something in the workspace while away. "Alexa, resume my thread." Show ThreadKeeper identify prior goal and detect the newly stale assumption/change.

### 1:25–1:55 — Drill-down

"What changed?" / "Why did I decide that?" Show evidence, not just prose.

### 1:55–2:20 — Handoff

Generate structured handoff to another agent/human.

### 2:20–2:45 — Under the hood

Concise architecture: Alexa+ -> real MCP -> Continuity Engine -> AWS AgentCore/Bedrock, plus evaluation.

### 2:45–3:00 — Proof/impact

Show truthful InterruptBench result if available and end on the product thesis.

## Never waste demo time

Avoid:

- login/setup;
- reading long text;
- code scrolling;
- generic architecture intro before the magic;
- every minor feature;
- claims that need verbal excuses.

## Submission readiness gate

- official current rules re-verified;
- selected track/mini challenges accurately represented;
- repo accessible as required;
- license/reviewer configuration correct;
- clean setup instructions checked;
- no secrets in git history/current repo;
- production/demo path checked;
- video public and under time limit;
- video English requirements satisfied;
- product feedback complete;
- friction logs truthful/actionable;
- benchmark claims reproducible;
- screenshots reflect current product;
- project submitted before internal target.

## Product feedback quality

Specific beats flattering. For every relevant Amazon tool/API/SDK capture:

- what we used it for;
- what worked;
- what failed/confused;
- onboarding experience;
- workaround;
- what would make us use it again.

Translate the strongest entries from `docs/FRICTION_LOG.md` rather than inventing feedback on submission day.
